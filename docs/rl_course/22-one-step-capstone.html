一、一个 PPO epoch 在干什么

一次 train_epoch() = 8 步集体采样 + GAE 算账 + 5 轮梯度更新。可以把它想成：N 个学徒同时练 8 拍动作，录成视频；教练回放视频，每段剪辑改一点点招式（PPO 裁剪），改 5 遍。

二、CPU 与 GPU 分工总览

训练时GPU 是主力：PhysX 物理、PyTorch 前向/反向、张量 buffer 都在 CUDA 上。CPU 负责：启动 Isaac Sim、Python 调度循环、TensorBoard 写盘、打印日志。瓶颈几乎总在 GPU 物理 + 采样，不是 CPU 算力。

3.1 t = 0 逐步放大（带 CPU/GPU 注释）

t=0 · 策略前向 [GPU]

PPO.model_act(self.obs) → RunningMeanStd(obs) → env_mlp(priv) → actor_mlp → 采样 a₀, V₀。PyTorch CUDA kernel 执行矩阵乘；CPU 在等 GPU 完成 Python 调用。

t=0 · 写入 buffer [GPU]

storage.update_data(..., n=0) 把 obs₀、priv₀、a₀、V₀、μ₀、σ₀ 拷进 storage_dict[:, 0, :]。预分配显存，无 malloc。

t=0 · Wrapper step [GPU]

GymStyleEnvWrapper.step(a₀) clamp → env.step。Python 在 CPU 跑，实际计算在 GPU。

t=0 · PhysX 物理 [GPU 瓶颈]

xhand_wave_env：动作→目标角→PD 力矩→PhysX 子步（sim.dt×decimation）→接触→奖励→更新 proprio_hist / priv_info。N 越大 GPU 越满。

t=0 · 奖励入账 [GPU]

r̃₀ = 0.01·r₀ + γV₀·timeout₀ → storage.rewards[0]；dones[0] 记录。episode 统计用原始 r，GAE 用 r̃。

t=0 完整调用栈 · 逐行 + 设备
代码 / 调用白话 + CPU/GPU
res_dict = model_act(self.obs)GPU 前向。输入 obs (N,186)、priv (N,8)。输出 actions (N,21)、values (N,1)。
storage.update_data('obses', 0, ...)GPU 写入。存 step 前的 s₀，不是 step 后的 s₁。
clamp(actions); env.step(...)GPU。Wrapper + PhysX。返回新 obs_dict → 覆盖 self.obs 为 s₁。
shaped_rewards = 0.01*r + ...GPU 元素运算。timeout 来自 Wrapper extras['time_outs']。
episode_rewards.update(...)GPU 索引 done env + CPU 侧 meter 滑动平均（标量 .item()）。

3.2 t = 1 … 7：重复与差异

t=1…7 与 t=0 代码路径完全相同，差异只有两点：① buffer 行号 n=1…7；② self.obs 已是上一步 PhysX 输出。GPU 时间线每步重复「前向 ~1ms 级 + PhysX ~数十ms 级（视 N 而定）」。8 步串行，无法并行——必须等 t=0 的 PhysX 完成才能用 s₁ 做 t=1 的 model_act。

3.3 post：8 步之后的 GPU 工作

play_steps 收尾 · 逐行 + 设备
代码白话 + CPU/GPU
model_act(self.obs)GPU。对 s₈（第 8 步后的状态）估 V₈，作 GAE 的 bootstrap 终端价值。
agent_steps += batch_sizeCPU 整数加法。+8×N。
computer_return(...)GPU。8 次逆序迭代，纯张量，相对 PhysX 可忽略。
prepare_training()GPU。展平 + advantage 标准化。
value_mean_std train/evalGPU。可选 normalize returns/values。
mini_epochs 循环 backwardGPU 密集。CPU 负责 Python 双层 for 调度 minibatch 索引。
问：num_envs=10 和 16384 时 GPU 在干什么差别？ 小 N：PhysX 欠饱和，GPU 大量空闲，EnvStepFPS 低。大 N：GPU 物理管线打满，采样 FPS 高，但显存占用线性增。RTX 5070 Ti 12GB 建议从 N=10 调试，再逐步加大。

十三、env done 后谁 reset？

某个并行 env 在 t=3 时 done=1，不是 Wrapper reset，而是 IsaacLab 环境内部 _reset_idx(done_ids) 在同一 env.step 调用里立刻重置该 env，并返回 reset 后的 obs。PPO 侧只看到 self.obs 已更新为新 episode 首帧；play_steps 不中断，继续 t=4…7。
问：8 步内 done 的 env GAE 怎么处理？ next_nonterminal = 1 - dones 在 done 步截断未来 bootstrap。该 env 的 trajectory 在 done 步「封口」，不影响同 batch 其他 env。

十四、如何 profile 验证 GPU 瓶颈

训练时在终端看 PPO 打印的 Collect Time vs Train RL Time：通常 Collect ≫ Train RL，说明 GPU 主要在 PhysX 而非 backward。TensorBoard 的 performance/EnvStepFPS 随 num_envs 增大应明显上升，直到显存打满。

问：play_steps 和 deploy 循环能共用 profiling 吗？ 不能简单共用：deploy 无 PhysX、无 backward，GPU 几乎只在 act_inference。训练 capstone 的 t=0…7 时间线专指 Stage 1 PPO play_steps。

十二、显存与 batch 心算

ExperienceBuffer 显存粗算（float32）
字段shapebytes（N=16384）
obses(8, N, 186)8×16384×186×4 ≈ 98 MB
actions/mus/sigmas(8, N, 21) ×3≈ 33 MB
其余字段values, rewards, dones…<20 MB
buffer 小计—~150 MB（相对 PhysX 很小）
显存大头在 N 个 PhysX 场景 与 网络权重，不在 ExperienceBuffer。这也是 horizon=8 而非 800 的原因之一——buffer 与 horizon 线性相关，但物理场景数 N 才是显存杀手。

十一、FAQ

问：8 步能并行跑吗？ 不能。t=1 的 model_act 依赖 t=0 PhysX 输出的 s₁，必须串行。能并行的是 N 个 env——它们在 GPU 上 batch 一起算。
问：headless 训练 GPU 利用率低正常吗？ 若 N 很小（如 10），PhysX batch 太小，GPU 会空转。加大 num_envs 直到显存接近上限，EnvStepFPS 会显著上升。
