部署到真机逐行精讲

训练好的"学生大脑"已经躺在一个 .pth 文件里。这一章我们把它接到一只真实的灵巧手上，逐个零件、逐行代码地看：它到底是怎么"看一眼手、算一个动作、发给电机"的。完全零基础也能跟下来。

读这章前的小提示。 如果你还没读过第 06 章（学生怎么来的）、第 10 章（整体流程）、第 11 章（sim-to-real 原理），没关系——本章会把用到的概念都用大白话再讲一遍。本章聚焦"代码怎么跑"，看的是仓库里 rl_isaaclab/deploy_xhand/ 这个文件夹。

一、部署到底在做什么

想象你已经请了一位"会转笔的高手"住进了一个 .pth 文件里。部署，就是给这位高手装上一双真手和一双真眼睛，然后让他不停地重复同一件事：
"看一眼现在手指弯成什么样、指尖碰到东西没 → 想一下下一步每根手指该动多少 → 动手把指令发给电机。"
每秒钟做 20 次，永远循环。就这么简单。难的不是循环本身，而是让真手上的每个数字，和他当年练习时（仿真里）看到的数字长得一模一样，他才不会"看错题"。

用一句话概括这个循环，它就是本章所有代码的主心骨：

$$\text{观测 } o_t \;\xrightarrow{\;\text{策略}\;}\; \text{动作 } a_t \;\xrightarrow{\;\text{换算}\;}\; \text{关节目标} \;\xrightarrow{\;\text{PD 电机}\;}\; \text{真手运动} \;\rightarrow\; o_{t+1}.$$

部署和训练有四个根本区别，记住它们，下面很多设计就都有了理由：

区别训练时（仿真）部署时（真机）
有没有仿真器有，物理引擎算一切没有，真手就是"物理引擎"
特权信息用（物体质量/摩擦等"上帝视角"）用不了，只能靠历史去"猜"
时间可以慢慢算、可加速必须实时，每步严格卡 1/20 秒
风险错了重开就行会伤人伤物，安全第一

二、两套部署代码的关系

这个项目里其实有两套部署代码，理解它们的关系，是看懂本章的钥匙：

原版 Sharpa（模板）Xhand 移植版（本项目要上的）
文件scripts/deploy.py + sharpa_wave_deploy_env.py整个 deploy_xhand/ 文件夹
手SharpaWave 灵巧手Xhand 1 Pro 灵巧手
动作维度2221
观测维度192186
单帧维度64 = 22+22+5+1562 = 21+21+5+15
打个比方：原版 Sharpa 部署代码是一份"菜谱"，已经被验证能做出一道菜。我们换了个牌子的厨房（Xhand），于是照着这份菜谱一行一行抄，只把"22 人份"改成"21 人份"（维度）。但有一件事不能照抄——灶台的操作面板（硬件 SDK）：Xhand 的 SDK 和 SharpaWave 完全是两套，所以碰硬件的那一个文件要按真实 Xhand SDK 重写。

这就引出一个聪明的工程决定（代码里叫 approach A），它把"照抄的部分"和"必须重写的部分"干净地隔开：

核心思想：把"碰硬件"的脏活，全关进一个小盒子里。
环境逻辑（deploy_env.py：拼观测、算动作、状态机、暖启动）逐行照抄 sharpa，全程只说一种"语言"——IsaacLab 的关节顺序、弧度制。所有真正要碰硬件 SDK 的动作，都被赶进 hw_interface.py 这一个文件。于是：
① 占代码大头的环境逻辑能和原版 Sharpa 几乎一字不差地对照、复用其正确性；
② 唯一需要"换灶台面板"的就只剩 hw_interface.py 一处；
③ 还能把这个"碰硬件的小盒子"换成一个假的（fake_hw.py），于是没有真手也能把整套流程跑通、还能写自动化测试。

代码已更新（重要）。 hw_interface.py 现在已按真实 Xhand SDK（容器内 introspect 出的 hand_controller 0.1.49）重写，不再是 SharpaWave 的接口。最直接的后果有两个，本章后面会展开：
• 关节指令变成了逐关节构造 Green_JointCommand_User（带 kp/kd/position/speed/torque/mode）再 set_joint_cmd_list 批量下发（第七节）；
• Xhand 的触觉根本不是 SharpaWave 的 6 轴力 F6——它是每根手指 3 块触觉 pad、每块 pad 一个 taxel 阵列 + 法向/切向力（第九节，整节已重写）。

四、一次控制循环：主程序长什么样

先看最外层的入口 deploy_xhand.py。剥掉参数解析，它的主循环短得惊人——这正是 approach A 的功劳，复杂度都被藏进了零件里：

deploy_xhand/deploy_xhand.py · main（节选） 
hw  = build_hw(cfg, args.dry_run)        # 真手 or 假手
hw.connect()                             # 连上
env = XhandInhandRotateDeployEnv(cfg, hw)        # 组装环境
runner = PolicyRunner(env, args.load_path, device=args.device)  # 装载大脑

obs = env.reset()                        # 暖启动抓取，拿到第一帧观测
try:
    while True:
        a   = runner.act(obs)            # ① 大脑：观测 → 动作
        obs = env.step(a)                # ② 手：执行动作（内含 20Hz 节拍），返回新观测
except KeyboardInterrupt:                # Ctrl-C
    print("急停: 断连")
finally:
    hw.disconnect()                      # 不管怎样，最后一定松手断连
整段就一句话：反复 act → step。act 是"想"，step 是"做"。step 里面会"睡"一小会儿，保证整圈刚好 1/20 秒。最妙的是那个 finally：无论是正常结束、报错、还是你慌乱中按了 Ctrl-C，程序一定会松手断连，不会让手卡在一个危险姿势上死命用力。这是真机安全的最后一道闸。

五、大脑：PolicyRunner 怎么把观测算成动作

policy_runner.py 负责"想"。它加载的是学生策略（第 06 章蒸馏出来的那个，文件名里叫 student_t603.pth），推理只有几行：

deploy_xhand/policy_runner.py · act 
@torch.no_grad()                          # 部署不需要算梯度
def act(self, obs_dict):
    inp = {
        "obs":          self.agent.running_mean_std(obs_dict["obs"]),       # 归一化当前观测
        "proprio_hist": self.agent.sa_mean_std(obs_dict["proprio_hist"]),  # 归一化历史
    }
    mu = self.agent.model.act_inference(inp)   # 学生算出动作"均值"
    return torch.clamp(mu, -1.0, 1.0).cpu()    # 夹到 [-1, 1]

这里藏着两个新手最容易栽跟头的点，务必记住：

易错点 ①：部署只取均值，不采样。 训练时策略是个"高斯分布"（第 03 章），会随机抽动作来探索。但真机上你要的是稳定、可复现的行为，所以调 act_inference 直接取分布的均值 μ，不再掷骰子。
易错点 ②：归一化的"尺子"也要一起加载。 running_mean_std（给观测用）和 sa_mean_std（给历史用）是训练时统计出来的均值方差（第 08 章）。部署时它们被冻结。少加载任何一个，输入分布就会偏移，策略行为漂移。

还有一个非常具体的工程坑，注释里写得很清楚——显卡不一致问题：

deploy_xhand/policy_runner.py · 加载权重（CPU-safe） 
# t603 在 CUDA 上训练保存；真机部署容器常是 CPU-only torch。
# 直接 torch.load 不带 map_location 会崩（试图反序列化到 CUDA 设备）。
ckpt = torch.load(ckpt_path, map_location=device)        # 显式按当前设备加载
self.agent.running_mean_std.load_state_dict(ckpt["running_mean_std"])
self.agent.model.load_state_dict(ckpt["model"])
self.agent.sa_mean_std.load_state_dict(ckpt["sa_mean_std"])
self.agent.set_eval()                                    # 切到推理模式
原版 Sharpa 怎么做的？ 原版 scripts/deploy.py 用 agent.restore_test(resume_path) 一行搞定加载，但它内部 torch.load 没带 map_location。移植版为了能在无 GPU 的部署机上跑，手动拆成上面"三件套"加载——逻辑等价，只是更安全。

六、观测怎么拼成 186 维

策略是个挑剔的考生，只认训练时那套"题面格式"。所以部署时拼观测，必须一字不差地照训练时的样子来。好在这部分代码和原版 Sharpa 几乎完全一样，只是把 22 改成 21。

每个控制步，手会给我们一帧"快照"，叫单帧观测，62 个数：

$$\underbrace{62}_{\text{单帧}} \;=\; \underbrace{21}_{\text{归一化关节角}} \;+\; \underbrace{21}_{\text{控制目标}} \;+\; \underbrace{5}_{\text{指尖触觉}} \;+\; \underbrace{15}_{\text{接触点(默认全 0)}}.$$

关节角要先用 unscale 归一化到 $[-1,1]$，保证和训练同一把尺子：

$$\hat q \;=\; \frac{2q - (q_{\max}+q_{\min})}{q_{\max}-q_{\min}}.$$

然后把最近 3 帧拼起来 $= 62\times 3 = 186$ 喂给主干；同时把最近 30 帧留给学生的 TConv 去"猜"看不见的物理属性（第 06、07 章）：

deploy_xhand/deploy_env.py · compute_observations（节选） 
cur = unscale(self.hand_dof_pos, lower, upper).unsqueeze(1)   # 关节角，同一归一化
cur = torch.cat([cur, self.cur_targets.unsqueeze(1)], dim=-1)         # 拼上控制目标
cur = torch.cat([cur, sensed_contacts, contact_pos], dim=-1)         # 拼上触觉 + 接触点
self.obs_buf_lag_history = torch.cat([prev, cur], dim=1)             # 推进滑动窗口
obs_buf = self.obs_buf_lag_history[:, -3:].reshape(num_envs, -1)     # 最近 3 帧 → 186
self.proprio_hist_buf[:] = self.obs_buf_lag_history[:, -30:]         # 最近 30 帧 → 给 TConv
"控制目标"为什么也是观测的一部分？ 因为策略需要知道"我上一步刚命令手指去哪了"，才能判断这一步该怎么补。这是增量式控制的常见做法，下一节就会用到它。

七、动作怎么落到电机上

策略吐出的动作 $a\in[-1,1]^{21}$ 不是直接的角度，而是一个"在上次目标基础上微调多少"的增量。两步走：

deploy_xhand/deploy_env.py · _pre_physics_step（算目标） 
actions = saturate(actions, -clip_actions, clip_actions)              # 先把动作夹进 ±1
# 增量式：新目标 = 上次目标 + 步长 × 安全系数 × 动作
targets = self.prev_targets + self.cfg.action_scale * self.cfg.action_scale_mul * actions
self.cur_targets = saturate(targets, lower, upper)                    # 再夹进关节限位
$$\text{target}_t \;=\; \text{clip}\Big(\text{target}_{t-1} + \underbrace{\tfrac{1}{24}}_{\text{action\_scale}}\cdot \underbrace{\mu}_{\text{安全系数}}\cdot\, a_t,\;\; q_{\min},\, q_{\max}\Big).$$

算好目标后，发给硬件层（环境只管发"IsaacLab 顺序的 21 个目标角 + kp + kd"，怎么变成 SDK 指令是 hw_interface 的事）：

deploy_xhand/deploy_env.py · _apply_action（环境侧下发） 
self._refresh_lab()                                                # 先读回当前关节角
self.hw.set_joint_targets(self.cur_targets.squeeze(0).cpu().numpy(),
                          self.cfg.kp, self.cfg.kd)               # 发目标 + PD 增益
self.prev_targets = self.cur_targets.clone()                      # 记住这次目标，下步要用

电机内部按 PD 公式算力矩去逼近目标，这是物理执行的最后一环：

$$\tau \;=\; k_p\,(\text{target}-q) \;-\; k_d\,\dot q.$$

硬件层怎么把目标变成真实 Xhand 指令（代码已更新）

这是本次代码更新的关键一处。真实 Xhand SDK 没有"一次设全部关节"的简单接口，而是要为每一个关节构造一个 Green_JointCommand_User 对象，再批量下发：

deploy_xhand/hw_interface.py · set_joint_targets（真实 SDK） 
xt = isaaclab_to_xhand(targets_isaaclab)        # ① 先把 21 个目标翻译成 Xhand 关节顺序
cmds = []
for i in range(21):                             # ② 逐关节构造一条指令
    c = self.hc.Green_JointCommand_User()
    c.position = float(xt[i])                   #   目标角
    c.kp = float(kp); c.kd = float(kd)          #   PD 增益
    c.speed  = float(self.cfg.cmd_speed)        #   ⚠️ 默认 0 很可能=不动！必须显式设非零
    c.torque = float(self.cfg.cmd_torque)
    c.mode   = self.cfg.joint_cmd_mode          #   位置控制 mode 取值（B1 真机确认）
    cmds.append(c)
self.hand.set_joint_cmd_list(cmds)              # ③ 批量一次性发给手
新手最易踩的雷：speed 默认 0 可能 = 不动。 很多电机指令结构里 speed=0 不是"不限速"，而是"速度上限为 0 → 关节纹丝不动"。所以代码显式把 cmd_speed 设成非零（占位 350，沿用 SharpaWave 数值）。这个字段的真实单位与语义属于 B1 待真机确认项——如果上电后手"收到指令却不动"，第一个要怀疑的就是它。
那个 action_scale_mul 是什么？ 这是移植版新增的一个安全旋钮（原版 Sharpa 没有，等价于固定为 1.0）。它就是一个 0~1 的"音量键"：第一次上真机时设成 0.3，让手的每一步都只走"三成力气"，确认安全后再调回 1.0。详见第十二节安全分级。

八、关节重映射：同一只手，两套编号

IsaacLab（策略说的话）和 Xhand 固件（手听得懂的话）对 21 个关节的编号顺序不一样——就像同一支球队，仿真按身高排号、真机按位置排号。发指令前必须"翻译"一下号码，否则你想弯食指，真手却去弯了拇指。

joint_map.py 用两个互为逆的"置换索引"来回翻译：发指令时 IsaacLab→Xhand，读状态时 Xhand→IsaacLab。

deploy_xhand/joint_map.py 
def isaaclab_to_xhand(v):     # 下发前：策略顺序 → 固件顺序（scatter）
    out = np.empty_like(v); out[ISAACLAB2XHAND_IDX] = v; return out

def xhand_to_isaaclab(v):     # 读回后：固件顺序 → 策略顺序（gather）
    return v[ISAACLAB2XHAND_IDX]
当前是"恒等占位"！ 代码里 ISAACLAB2XHAND_IDX = list(range(21)) 只是个临时的"原样不动"占位。B2 真机到位后，要用 scripts/inspect_xhand_joints.py 实测出真实的对应关系再替换。这一步搞错，手会做出完全错误的动作。
关节重映射可视化（21 DOF）
左列 IsaacLab 策略序，右列 Xhand 固件序，连线是 isaaclab→xhand 的对应。悬停任意关节高亮它去了哪儿。当前演示的是"恒等占位"（一一对应），B2 实测后连线会变成交叉的真实排列。

九、触觉的 sim-to-real

触觉是这个项目的特色，也是现实落差的重灾区。这一节先把"真机的触觉传感器到底是个什么东西"讲透，再讲它怎么和仿真对齐。

真机的触觉传感器是什么东西

你闭着眼也能把手机从口袋里摸出来、能感觉到水杯快滑了赶紧握紧——靠的就是指腹皮肤里成千上万个触觉感受器。给机械手装触觉传感器，就是给它的指尖贴上一层"电子皮肤"：一小块能测"被压了多重、往哪个方向压"的力敏贴片。没有它，手就像戴着厚手套干活，物体在掌心打滑了都不知道。

具体到本项目的 Xhand 1 Pro，它的触觉系统是这样的（来自 xhandSDK/ 官方文档）：

Xhand 1 Pro 触觉硬件构成
部件数量 / ID说明
掌板1 块整只手的"主板"，汇总通信
指关节板21 块每个关节一块，带唯一 ID
指节触觉传感器18 个贴在指节上的"电子皮肤"，每个有唯一 sensor id
无触觉的关节ID 0/4/8/12/16/20这几个指节没有触觉传感器
掌心触觉传感器ID 30/31/32手掌心的 3 个特殊触觉板

每个触觉传感器本质是一块小小的力敏阵列（taxel array）：表面密布很多个微小感应点（taxel），当指尖压到物体上，贴片发生微小形变，电路把每个点的形变换算成读数。

代码已更新：Xhand 的触觉跟 SharpaWave 完全不是一回事！ 我之前按 SharpaWave 的"6 轴力 F6"讲过，但实测真实 Xhand SDK（容器 introspect）后发现结构完全不同，这一节已据此重写。务必记住下面这套 Xhand 的真实模型。

Xhand 触觉的真实数据结构

在 Xhand 上，每根手指有 3 块触觉 pad（在 SDK 里叫 Haptic_FingerSensors，分别记作 tip / pad1 / pad2，大致是指尖和指腹的两段）。每一块 pad 读出来是一个 Green_Sensor_User 对象，里面信息很丰富：

单块 pad 的数据（Green_Sensor_User 关键字段）
字段含义
first_ydds_nf
second_ydds_nf		法向力（normal force）：垂直压进皮肤的力，"压得多重"
first_ydds_tf
second_ydds_tf		切向力（tangential force）：沿皮肤表面的力，"有没有要滑"
channelDatataxel 阵列：这块皮肤上每个感应点的原始读数
sProxData接近觉（还没碰到时就能感到物体靠近）
sensor_id这块 pad 的唯一编号

取数据的接口也变了：不是一次读一个，而是 get_sensor_state_list(True) 一次性把所有 pad 读回来（再加掌心传感器），返回 (错误码, 消息, pad 列表, 掌心)。

从"一堆 pad"到"每指一个数"

策略其实只需要回答一个朴素问题："这根手指现在压得多紧？" 所以代码把每根手指那 3 块 pad 的法向力加起来，得到一个标量，5 根手指就是 5 个数：

$$\text{指}_k\text{的力} \;=\; \sum_{\text{pad}\in\{tip,\,pad1,\,pad2\}} \big(\text{first\_ydds\_nf} + \text{second\_ydds\_nf}\big).$$
deploy_xhand/hw_interface.py · get_tactile_raw（真实 Xhand SDK） 
code, msg, sensors, _palm = self.hand.get_sensor_state_list(True)  # 一次读回所有 pad
by_id = {int(s.sensor_id): s for s in sensors}                    # 按 sensor_id 建索引
out = np.zeros(5, dtype=np.float32)
for k, (tip, pad1, pad2) in enumerate(FINGER_SENSOR_LAYOUT):      # 每指 3 块 pad
    f = 0.0
    for sid in (tip, pad1, pad2):
        s = by_id.get(sid)
        if s is not None:
            f += float(s.first_ydds_nf) + float(s.second_ydds_nf)  # 累加法向力
    out[k] = f                                                    # 这根手指一个标量
return out                                  # (5,) [拇, 食, 中, 无名, 小]
为什么敢这么狠地降维（从一堆 taxel 阵列压成 5 个数）？ 因为"转圆柱"任务策略真正在乎的是"每根手指有没有踩稳、压力够不够"，并不需要知道压在皮肤哪个点、力朝哪个细微方向。降到 5 个标量，更抗噪、也最容易让仿真和真机对齐——这正是它必须和训练时的"5 维指尖力"长一模一样的原因。
更"正统"的做法（B3 升级项）： SDK 还提供 HapticModel.compute_all_fingers(...)，能把每根手指那几块 pad 的阵列数据更科学地融合成每指一个力（但需要先做 Haptic_Config 标定）。一期先用上面这个"法向力直接相加"的稳妥版本，跑通后再升级。

仿真 ↔ 真机怎么对齐

不管真机底层多复杂，最后都对齐成同一个"5 维指尖力"，顺序固定为 [拇指, 食指, 中指, 无名指, 小指]。分工很清晰：tactile_map.py 只管"每指是哪 3 块 pad、5 指什么顺序"（FINGER_SENSOR_LAYOUT），返回原始力；缩放、阈值、二值化这些"加工"全交给 deploy_env.get_tactile_info（这部分逐行照搬 sharpa，没变）：

deploy_xhand/deploy_env.py · get_tactile_info（真机侧加工，照搬 sharpa） 
force = torch.tensor(self.hw.get_tactile_raw())   # (5,) 原始指尖力（已是每指法向力之和）
force *= self.cfg.force_scale                     # ×(1/1.5)，缩放到训练量纲
force[force < self.cfg.contact_threshold] = 0.0   # 噪声门：太小的力当作没碰到
if self.cfg.binary_contact:                       # 可选：只关心"碰没碰"
    force = torch.where(force > thresh, 1.0, 0.0)
仿真真机（Xhand）
力从哪来物理引擎算出的接触净力范数每指 3 块 pad 的法向力之和
加工平滑 + 延迟 + 噪声（第 09 章故意加的）force_scale 缩放 + 阈值噪声门
标定无需上电先 sensor_clear 把基线归零（按 t）

force_scale = 1/1.5 的作用就是把真机测到的力缩放到训练时那把"尺子"的量纲——仿真里 1 单位力和真机 pad 读出来的数值不一定是一回事，必须乘一个系数对齐，否则策略会觉得"怎么这么使劲/这么没劲"。这个系数也是 B3 真机标定项。

为什么上电必须先"标定归零"

真实的力敏 pad 有个毛病：明明什么都没碰，读数也不是 0——可能因为出厂偏置、温度变化（手干一会儿会发热）、或装配时的预压。这叫零点漂移。标定就是趁手悬空、没碰任何东西时，告诉传感器："记住，现在这个读数就算 0。" 之后的力都相对这个基线来算。不标定，策略会以为指尖一直被按着，从一开始就判断错。

对应到真实 Xhand SDK，部署里按 t → env.calib_tactile() → hw.calib_tactile()，底层调的是 SDK 的 sensor_clear()（命令行对应 -f sensor_clear，可单个或全部清零）。

占位提醒（真机到位才能定）。 B3 tactile_map.py 里的 FINGER_SENSOR_LAYOUT（每指 tip/pad1/pad2 的 sensor_id）是占位，要实测确认；法向力字段 first_ydds_nf/second_ydds_nf 的语义、是否够用（还是改走 HapticModel）、以及 force_scale/阈值都需真机标定。 B1 get_sensor_state_list 的 bool 参数（是否 flush）等行为，需用 scripts/inspect_xhand_sdk.py 在真机上核对。

十、先抓稳再转：warm-up 暖启动

学生只会"转"，不会"从零把物体抓起来"——它练习时，物体一开始就已经在手里了。所以真机上策略接管前，得先帮它把物体抓稳，摆好起手式。办法很朴素：回放一段预先录好的"合拢手指"动作，边合边摸，指尖一感觉到接触就停。
deploy_xhand/deploy_env.py · _reset_idx（warm-up 核心） 
traj = np.load(self.cfg.init_traj_path)        # 预录的抓取轨迹（一帧帧的关节目标）
tactile_force, _ = self.get_tactile_info()
j = 0
self.hw.set_joint_targets(traj[j], kp, kd)
while torch.max(tactile_force) < self.cfg.grasp_contact_thresh and j + 3 < len(traj):
    j += 1
    self.hw.set_joint_targets(traj[j], kp, kd)  # 再合拢一点
    time.sleep(0.03)
    tactile_force, _ = self.get_tactile_info()  # 摸一下：抓到了吗？
# 抓到了！以此刻姿态作为策略的起手式
grasp = torch.tensor(traj[j + 2])
self.prev_targets[env_ids] = grasp
self.cur_targets[env_ids]  = grasp
和原版 Sharpa 的唯一差异。 逻辑完全一致，只是原版直接对固件下发并做 dof_sharpa2isaaclab 转换，移植版改成走 self.hw 接口、轨迹文件换成 cache/deploy_init_traj_xhand.npy。--no_warm_up 或 --dry_run 时会跳过这一步。

十一、键盘安全状态机：人始终能接管

真机会伤人伤物，所以默认绝不自动跑。程序起来后手是静止的，必须你亲手按键才启动，而且随时能冻结、能回零位、能急停。这是不可逾越的安全底线。

env.step 每一步都先看一眼键盘状态标志，决定这一步做什么：

deploy_xhand/deploy_env.py · step（状态机骨架） 
deploy_state = self.deploy_state_flag.get()
if   deploy_state == 0:   # 初始 / 回零：手停在全 0 位
    self.hw.set_joint_targets(np.zeros(21), kp, kd)
elif deploy_state == 1:   # 冻结：锁住当前角度不动
    self.hw.set_joint_targets(self.hw.get_joint_pos(), kp, kd)
elif deploy_state == 2:   # 重置：重新 warm-up 抓取
    self._reset_idx([0])
elif deploy_state == 3:   # 运行：真正跑策略动作
    self._pre_physics_step(action); self._apply_action()
按键动作说明
e启动策略先重新 warm-up 抓一次（置位 2 → _reset_idx），抓稳后自动进入运行态（置位 3）
w冻结 / 继续锁住当前姿态（再按一次恢复之前的状态），便于观察或临时叫停
q回零位手回到安全的全 0 姿态
t触觉标定把指尖力的基线归零
Ctrl-C急停立刻停手并断连（第四节的 finally 兜底）

按键由后台线程 KeyboardListener（基于 pynput）抓取，通过一个线程安全标志位传给主循环——所以你按键时主循环照常 20Hz 跑，互不阻塞。

部署状态机（点按钮模拟按键）
e 启动 / w 冻结 / q 回零 / t 触觉标定。高亮当前状态。真机上 Ctrl+C 会安全停手并断连。
代码已更新：键盘需要 pynput + X11，容器里尤其要注意。 抓键盘靠 pynput，而 pynput 要能访问 X11 图形界面。在 Docker 容器里跑时，必须：① 主机先 xhost +local:root 放行；② 用 docker-compose 进容器（它挂了 /tmp/.X11-unix 并传了 DISPLAY，见下一节）。
现在代码做了友好处理：如果 keyboard_listen=True 但导入 pynput 或连 X11 失败，会抛出一句清晰的 RuntimeError（告诉你"要么挂 X11、要么加 --no_keyboard"），而不是神秘崩溃。
deploy_xhand/deploy_env.py · 键盘初始化的友好报错 
if self.cfg.keyboard_listen:
    try:
        from rl_isaaclab.utils.keyboard_listener import KeyboardListener
        from rl_isaaclab.utils.misc import ThreadSafeValue
    except Exception as e:   # pynput 缺失 / 无 X server 都会到这
        raise RuntimeError(
            "keyboard_listen=True 需要 pynput + X 访问(容器用 docker-compose 挂 "
            "/tmp/.X11-unix 并 `xhost +local:root`)。或用 `--no_keyboard` 自动跑。"
            f" 原始错误: {e!r}") from e

如果环境实在没有图形界面（比如机器人板载电脑、SSH 无 X），就用 --no_keyboard：程序会自动 warm-up 抓取后直接跑策略，靠 Ctrl-C 急停。真机首跑仍建议配合 --action_scale_mul 0.3 限幅。

十二、安全分级 S0–S4 与待标定项

第一次让 AI 控制一只真手，绝不能"满功率上场"。正确做法像学开车：先在空地上慢慢挪（低速、低力、限幅度），每过一关再放开一点。配置文件 deploy_cfg.py 里就是这些"挡位旋钮"。
deploy_cfg.py · 安全旋钮
参数值作用

kp / kd100 / 3PD 增益，写进每条 Green_JointCommand_User；B4 系统辨识后更新
dof_limits_scale0.9关节限位收紧到 90%，给关节留安全裕度

代码已更新：因为换到了真实 Xhand SDK，新增/变化了几个指令字段（都在每条 Green_JointCommand_User 里）：

deploy_cfg.py · Xhand 指令新增字段

一个容易混淆的点。 旧版（SharpaWave）靠 set_current_coeff/set_speed_coeff 全局限力限速；Xhand 没有这套，限速/限力得走每条指令的 speed/torque 字段或寄存器。所以 env 里仍会调 set_speed_coeff/set_current_coeff（照搬 sharpa 不改逻辑），但在 Xhand 的 hw_interface 里它们是 pass（什么都不做）。

代码里还有四处明确标注的"真机到位才能填"的占位，看到这些徽章就知道那行不是最终值：

B1 SDK 行为（Green_JointCommand_User 的 mode/speed/torque 取值与语义、get_*_state_list 的 bool 参数、comm.open() 成功枚举名）   B2 关节顺序映射（joint_map.py）   B3 触觉 FINGER_SENSOR_LAYOUT、法向力字段语义、缩放/阈值（tactile_map.py / cfg）   B4 PD 增益 kp/kd 系统辨识

十三、没有真手也能跑：dry-run / FakeHW

这是 approach A 最甜的果实。fake_hw.py 是一个和真硬件层接口完全一致的"假手"：你问它关节角，它返回一组 0；你发指令，它默默记下。于是整条部署链路在没有真手时也能完整跑通：

deploy_xhand/fake_hw.py（节选） 
class FakeHWInterface:
    def get_joint_pos(self):  return self._pos.copy()    # 假装返回当前关节角
    def get_tactile_raw(self): return self._tac.copy()   # 假装返回 5 指力
    def set_joint_targets(self, targets, kp, kd):
        self.last_targets = targets.copy()               # 只记录，不真的动
离线 dry-run（无硬件、无 pynput 也能跑） 
python -m rl_isaaclab.deploy_xhand.deploy_xhand \
    --dry_run --max_steps 50 \
    --load_path ckpts/scale_1000M/student_t603.pth
为什么这很重要？ 它让你能在买到真手之前就验证：观测维度对不对、策略能不能加载、循环会不会崩。仓库里的 tests/deploy_xhand/ 自动化测试就全靠它——用假手喂各种状态，断言观测拼装、关节映射、推理输出都正确。先在假手上跑通，再上真手，能避开 90% 的低级事故。

十四、为什么要用 Docker 容器部署（新增）

你可能会问：直接在自己电脑上 python deploy_xhand.py 不就行了？偏偏不行。厂商给的 Xhand SDK（那个 .deb 和 hand_controller 包）是专门给 Ubuntu 22.04 编译的，依赖 libfmt.so.8 这类特定版本的系统库；而本机是 Ubuntu 24.04（库版本对不上），根本装不上。Docker 就是一个"随身携带的、装好 Ubuntu 22.04 的小盒子"——在盒子里 SDK 开箱即用，还不污染你的主系统，将来原样搬到机器人板载电脑也能跑。

这套容器放在新增的 deploy_docker/ 目录里。设计上分得很清楚——哪些东西烤进镜像、哪些运行时才挂载：

内容为什么
烤进镜像
（build 时）		Ubuntu 22.04 + Xhand 系统 SDK(.deb) + Python 绑定(hand_controller) + CPU 版 torch + pynput这些很少变、装一次就好；换了它们才需重新 build.sh
运行时挂载
（run 时）		整个项目仓库（含代码、ckpts/ t603 权重、cache/ 关节表与暖启动轨迹）→ /workspace改部署代码立即生效，不用重建镜像
为什么是 CPU 版 torch（没装 GPU）？ 因为学生策略很小、Xhand 触觉又是直接读 taxel 阵列（不像 SharpaWave 那种需要 CUDA 跑视觉触觉），所以推理用 CPU 就够，镜像更瘦、也不用伺候 GPU 驱动。这也是本容器相比 SharpaWave 容器去掉了 nvidia runtime 的原因。

两种进容器方式

对应"真机还没到"和"真机到了要用键盘"两种场景：

十五、真机上手清单与命令速查

  • 环境：在 22.04 容器里跑（SDK 装得上）？import hand_controller 成功？串口透传了？

  • 动作下发：Green_JointCommand_User 的 speed 设了非零（默认 0 可能=不动）？mode 是位置控制取值？
  • 触觉：B3 的 FINGER_SENSOR_LAYOUT 对了？上电先 sensor_clear 标定？force_scale 对齐到训练量纲？
  • 动作幅度：取均值（act_inference）而非采样？首跑用了 action_scale_mul=0.3？限位收了 0.9 裕度？
  • 安全：warm-up 抓稳了再跑？键盘能冻结/回零（或 --no_keyboard + Ctrl-C）？
本章小结。 部署的本质就一句话：act → step 的无限循环。难点全在"让真手的每个数字对齐训练时的样子"——于是有了观测拼装、关节重映射、触觉缩放、归一化加载。再加上 warm-up 抓取解决"起手式"、键盘状态机与安全分级守住"不伤人伤物"、FakeHW 让"没真手也能验证"。原版 Sharpa 提供了被验证过的逻辑模板，Xhand 移植版逐行照抄并把"碰硬件"隔离进一个可替换的小盒子。至此，从训练好的 .pth 到真手转起物体，整条路你已经能逐行讲清了。
